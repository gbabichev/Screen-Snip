# 1.5.1: startup Escape and drag / Escape tests

Ran two additional sets of **100 real-input trials** against unchanged tag **1.5.1**, commit `08f2c0af639144f90033112e2835e26282ef678a` (Release - Web build). The editor was confirmed closed before every hotkey; the application stayed running and Finder was foreground.

| Scenario | Attempts | Confirmed overlays | Editor reopens | New snip files observed |
| --- | ---: | ---: | ---: | ---: |
| Escape around capture startup | 100 | 100 | 0 | 0 |
| Hold mouse, drag, Escape, release | 100 | 100 | 0 | 0 |

## Startup timing

**76/100 first Escape presses did not cancel the pending capture.** In those trials the overlay appeared afterward and remained until a separately logged cleanup Escape. Those are not claimed as successful first cancellations. The other 24 trials cancelled without cleanup. No editor reopened in either case.

| Requested Escape delay from hotkey (ms) | Trials | Median actual delay (ms) | Needed cleanup Escape |
| ---: | ---: | ---: | ---: |
| 40 | 13 | 63.5 | 13 |
| 75 | 13 | 86.5 | 13 |
| 125 | 13 | 140.0 | 13 |
| 200 | 13 | 212.1 | 13 |
| 300 | 12 | 319.1 | 12 |
| 400 | 12 | 416.2 | 12 |
| 475 | 12 | 495.7 | 0 |
| 550 | 12 | 566.1 | 0 |

This matches the baseline's ordering: screenshot acquisition precedes selection presentation, and Escape registration/local monitoring are installed during selection presentation (`Selection.swift`, `installEscapeHotKey()` / `keyMonitor`). It explains the missed very-early Escape behavior, not the reported editor-reopen bug.

## Dragging

All **100/100** drags were verified using the app's visible selection-size label and the system's left-button-held state immediately before Escape. All **100/100** overlays dismissed before mouse-up. The left-button state was still held at the end of the pre-release observation in **100/100** trials.

Each trial observed for 400 ms after Escape before sending mouse-up, then for another 1.5 seconds after release. No editor reopened, no cleanup drag was needed, and no new image file was observed in the configured/default snip folders.

## Limits and artifacts

These tests did **not reproduce the editor reopening**. They do not prove the intermittent bug is absent, cover other Spaces/display configurations, or watch indefinitely after cancellation. No application source fixes were applied; the earlier commit remains stashed.
